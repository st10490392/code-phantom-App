## Protocol and authorization

GET /api/v1/ea/gilgamesh uses authenticated EA entitlement access and returns only the caller's sessions, safe broker events, timestamped position observations and per-session reported net realized P/L. It never aggregates unrelated account currencies. Signal publication is not a receipt or fill.

POST /api/v1/ea/gilgamesh/bindings requires admin.system and a nonsecret owner authorization reference. The owner must independently verify account ownership, explicit DEMO authorization, exact broker account/server, active licensed device and owned EA integration before calling it. The API cannot itself validate an external broker proof. Sessions remain SHADOW, and order submission is unavailable. POST /bindings/:id/revoke is audited. Binding identities are unique while active.

POST /api/v1/integrations/ea/demo-events uses an EA_INSTANCE key with ea.heartbeat scope and additionally requires the exact admin-authorized session/key/owner/account/server binding, current DEMO entitlement, active core licence and device. Existing keys gain no unbound access. Unknown fields (passwords, strategy/research data) are rejected. Schema v1 records INTENT/UNCERTAIN/REJECTED/EXECUTED receipts separately from broker fill/position/partial/final close/BE/trail events. EXECUTED requires a broker order identity and does not prove a full fill. Uncertain receipts never authorize a retry. Late broker observations retain their own timestamps; delivery sequence is monotonic. Positive broker deal identities are unique per session. Outcome math includes confirmed opening fees and closing profit/commission/swap; broker observations remain historical rather than a claim of current connectivity.

The broker reporter in the paired Scanner branch reads actual broker history and positions without order submission. It reconstructs partial volumes from full history; missing history, unsupported reversals and incomplete volume remain errors. The durable SQLite outbox delivers identical evidence after restart. Owner/runtime configuration and attachment to the verified operational runner are still required; no running process was changed.
